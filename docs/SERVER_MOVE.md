# جابه‌جایی فرفرو از یک سرور به سرور دیگر

هر بار که سرور عوض می‌شود، همین راه را برو. هدف این است که هیچ داده‌ای گم نشود و سایت فقط چند دقیقه صفحهٔ «چند دقیقه دیگر برمی‌گردد» نشان دهد.

## فرفرو روی سرور چه چیزهایی دارد

فقط سه چیز. اگر هر سه منتقل شوند، سرور جدید دقیقاً همان سرور قبلی است:

| چه | کجا | چرا مهم است |
|---|---|---|
| دیتابیس | Postgres | همهٔ حساب‌ها، نوبت‌ها، پرداخت‌ها و عکس‌ها (عکس‌ها داخل دیتابیس‌اند) |
| فایل env | `/srv/frfro/.env` (یا هر جا که `FRFRO_ENV_FILE` می‌گوید) | اگر `FRFRO_ADMIN_SECRET` یا کلیدهای VAPID عوض شوند، Authenticator مدیرها و اعلان کاربرها باطل می‌شوند |
| گواهی HTTPS | `/etc/letsencrypt` | با گواهی آماده، سرور جدید از همان لحظهٔ اول HTTPS دارد. frfro.ir به مرورگرها گفته فقط با HTTPS باز شود (HSTS)، پس بدون گواهی سایت اصلاً باز نمی‌شود |

برنامه چیز دیگری روی دیسک نگه نمی‌دارد. کد از GitHub می‌آید.

## ابزارها

- `scripts/move-export.sh`: روی سرور قدیم. هر سه را در یک فایل `.tar` می‌گذارد، همراه با تعداد ردیف‌های هر جدول و یک checksum. اگر وسط کپی چیزی در دیتابیس نوشته شود، قبول نمی‌کند و می‌گوید اول حالت نگهداری را روشن کن.
- `scripts/move-import.sh`: روی سرور جدید. checksum را چک می‌کند تا فایل در راه خراب نشده باشد. فقط روی دیتابیس خالی برمی‌گرداند. بعد تعداد ردیف‌های **همهٔ جدول‌ها** را با سرور قدیم مقایسه می‌کند و اگر یکی فرق داشته باشد، می‌ایستد.
- حالت نگهداری (در `deploy/nginx.conf`): وقتی فایل `/var/www/frfro/maintenance` باشد، nginx به همه صفحهٔ `deploy/maintenance.html` را نشان می‌دهد و هیچ درخواستی به برنامه نمی‌رسد. پس در این مدت چیزی در دیتابیس نوشته نمی‌شود.
- `deploy/nginx-forward.conf`: برای سرور قدیم بعد از جابه‌جایی. گوشی‌هایی که هنوز آدرس قدیم را دارند، به سرور جدید فرستاده می‌شوند. پس کسی روی دیتابیس قدیم نمی‌نویسد.

## از چند روز قبل

- [ ] سرور جدید را طبق `docs/DEPLOY_SERVER.md` آماده کن، ولی **migrate و کپی داده را نکن**. Node، Postgres، nginx، certbot، کاربر و یک دیتابیس خالی کافی است.
- [ ] یک بار تمرین کن: export از سرور قدیم **بدون** حالت نگهداری (اگر قبول نکرد، ساعتی خلوت‌تر امتحان کن) و import روی سرور جدید. اگر تعدادها یکی بود، راه سالم است. بعد همان دیتابیس را با `FORCE=1` روز جابه‌جایی دوباره پر می‌کنی.
- [ ] TTL رکوردهای DNS را کم کن (۶۰ تا ۳۰۰ ثانیه)، حداقل یک روز قبل. در DNS ورسل همین حالا ۶۰ است.
- [ ] یک بکاپ تازه را از سرور بیرون ببر (پایین، «بکاپ بیرون از سرور»).

## روز جابه‌جایی (ساعت خلوت، حدود ۱۵ دقیقه)

`OLD` و `NEW` آدرس دو سرورند. فرض شده مسیرها مثل `docs/DEPLOY_SERVER.md` هستند. اگر نه، `FRFRO_ENV_FILE` را بده.

۱. **سرور قدیم، حالت نگهداری را روشن کن.** از این لحظه سایت صفحهٔ «چند دقیقه دیگر» را نشان می‌دهد.
```bash
sudo mkdir -p /var/www/frfro && sudo cp /srv/frfro/app/deploy/maintenance.html /var/www/frfro/
sudo touch /var/www/frfro/maintenance
```

۲. **سرور قدیم، بسته بساز:**
```bash
sudo /srv/frfro/app/scripts/move-export.sh /root/move
```
آخرش تعداد جدول‌ها و کاربرها را می‌گوید. یادداشتش کن.

۳. **بسته را مستقیم به سرور جدید ببر.** همهٔ رمزها داخلش است، پس جای دیگری نفرست:
```bash
scp /root/move/frfro-move-*.tar* root@NEW:/root/move/
```

۴. **سرور جدید، برگردان و بررسی کن:**
```bash
sudo /srv/frfro/app/scripts/move-import.sh /root/move/frfro-move-<تاریخ>.tar
```
- اگر env روی سرور جدید نبود، env سرور قدیم را می‌گذارد و می‌ایستد. `POSTGRES_URL` را به دیتابیس سرور جدید عوض کن و دوباره اجرا کن.
- اگر بگوید کلیدی با سرور قدیم فرق دارد، قبل از ادامه همان کلید را از سرور قدیم بردار، مگر عمداً عوضش کرده باشی.
- باید بنویسد `row counts identical to the old server`. اگر ننوشت، **ادامه نده**. سرور قدیم هنوز سالم است: فایل maintenance را پاک کن تا سایت مثل قبل کار کند، و مشکل را پیدا کن.

۵. **سرور جدید، بالا بیاور:**
```bash
sudo -u frfro /srv/frfro/app/scripts/deploy.sh
```
اگر گواهی آمده بود (`/etc/letsencrypt`)، nginx را با همان گواهی تنظیم کن (`certbot install --nginx -d frfro.ir -d www.frfro.ir --cert-name frfro.ir`). بعد از کامپیوتر خودت، بدون عوض کردن DNS، نسخهٔ جدید را امتحان کن:
```bash
curl --resolve frfro.ir:443:NEW https://frfro.ir/api/health
```
با یک حساب واقعی هم وارد شو (فایل hosts کامپیوترت را موقتاً به NEW ببر): پروفایل، عکس‌ها و نوبت‌ها باید سر جایشان باشند.

۶. **سرور قدیم، به سرور جدید بفرست:** `deploy/nginx-forward.conf` را با آدرس NEW جای سایت فعلی بگذار، `nginx -t`، بعد `systemctl reload nginx`. بعد فایل maintenance را پاک کن و `systemctl stop frfro` بزن. حالا هر کس به سرور قدیم برسد، در واقع روی سرور جدید است. روی سرور جدید هم `set_real_ip_from OLD; real_ip_header X-Real-IP;` را اضافه کن (توضیحش در همان فایل است).

۷. **DNS را عوض کن:** رکوردهای `frfro.ir` و `www` را به NEW ببر. از اینجا به بعد کسی چیزی را از دست نمی‌دهد، چون آدرس قدیم و جدید هر دو به یک دیتابیس می‌رسند.

۸. **سرور جدید، کارهای بعدی:** crontab (`deploy/crontab`)، بکاپ شبانه، `certbot renew --dry-run`. بعد پایش `https://frfro.ir/api/health` را چک کن.

۹. **سرور قدیم را یک هفته نگه دار** (فقط برای فرستادن). بعد خاموشش کن. بسته‌های `/root/move` را روی هر دو سرور پاک کن.

## اگر بعد از جابه‌جایی مشکل جدی پیدا شد

- **قبل از مرحلهٔ ۶:** فایل maintenance سرور قدیم را پاک کن. سایت روی سرور قدیم مثل قبل کار می‌کند و هیچ چیز گم نشده.
- **بعد از مرحلهٔ ۶:** داده‌های تازه روی سرور جدید نوشته شده‌اند. برای برگشتن، همین راه را برعکس برو: export روی سرور جدید و import روی سرور قدیم با `FORCE=1`. **دیتابیس قدیم را بدون export تازه دوباره روشن نکن**، وگرنه نوبت‌های این فاصله گم می‌شوند.

## بکاپ بیرون از سرور

بکاپ شبانه (`scripts/backup-db.sh`) روی همان دیسک است و با از دست رفتن سرور از بین می‌رود. هفته‌ای یک بار آخرین بکاپ را بیرون ببر، مثلاً روی کامپیوتر ویندوز خودت در PowerShell:
```powershell
scp "root@SERVER:/srv/frfro/backups/$(ssh root@SERVER 'ls -t /srv/frfro/backups | head -n1')" "$HOME\frfro-backups\"
```
بکاپ شبانه فقط دیتابیس است. env را یک بار جای امنی نگه دار، مثلاً در یک مدیر رمز. بدون آن، با بکاپ می‌شود داده را برگرداند، ولی مدیرها باید Authenticator را دوباره راه بیندازند.

## جابه‌جایی اول: از Vercel و Supabase به سرور (یک بار)

Vercel سرور نیست. نه حالت نگهداری دارد و نه export، پس این بار با دو تفاوت:

- **داده:** `pg_dump` مستقیم از Supabase (`docs/DEPLOY_SERVER.md`، «آوردن داده از Supabase»)، بعد `scripts/pull-media-from-storage.mjs` برای عکس‌ها. چون نمی‌شود Vercel را در حالت نگهداری گذاشت، این کار را در ساعت خلوت و درست قبل از عوض کردن DNS بکن. بعد با `scripts/db-counts.sh` تعدادها را روی Supabase و سرور مقایسه کن.
- **گواهی:** چون گواهی‌ای برای آوردن نیست، و DNS دست ورسل است، گواهی را **قبل** از عوض کردن DNS با رکورد TXT بگیر تا سایت حتی یک لحظه بدون HTTPS نماند:
  ```bash
  certbot certonly --manual --preferred-challenges dns -d frfro.ir -d www.frfro.ir
  ```
  certbot دو مقدار `_acme-challenge` می‌دهد. آن‌ها را به Claude بده تا در DNS ورسل بگذارد. وقتی گذاشت، Enter بزن. بعد `certbot install --nginx --cert-name frfro.ir`. تمدید خودکار با این روش کار نمی‌کند. وقتی DNS روی سرور آمد، یک بار `certbot certonly --nginx --cert-name frfro.ir -d frfro.ir -d www.frfro.ir --force-renewal` بزن تا تمدید از این به بعد خودکار باشد. بعد `certbot renew --dry-run`.

از جابه‌جایی دوم به بعد، همهٔ این‌ها با همان راه اصلی بالا انجام می‌شود.
