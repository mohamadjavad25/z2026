## 2026-10-01 — یکدست‌سازی کامل response envelope به `{data: ...}`
- **رفع شد**: هر ۱۸ route بک‌اندی که قبلاً یا کلید legacy در کنار `data` داشتن (مثل `{profile, data:{user}}`) یا اصلاً هیچ `data` نداشتن (مثل `{bookings: [...]}`) الان همه فقط `{data: {...}}` برمی‌گردونن — شامل auth (login/me/register)، profile و profile/settings، beauty-passport، salon-follow، salons و salons/[id]، و تمام route های مدیریت سالن (bookings, collabs, hours, invites, portfolio, services, staff) و artist-bookings/artist-hours. بدنه‌ی مسیرهای خطا (`{error, code, ...}`) دست‌نخورده موند — این فقط envelope موفقیت رو یکدست کرد.
- **یک باگ واقعی پیدا و رفع شد حین این کار**: دو جای `HomeApp.jsx` (باز کردن جزئیات سالن) داشتن `detailPayload.salon || detailPayload` می‌خوندن — یعنی اگه کلید `salon` نبود (که بعد از این تغییر دقیقاً همین اتفاق می‌افتاد)، کل آبجکت خام پاسخ (شامل `data`) به‌جای فقط فیلدهای سالن merge می‌شد؛ این سکوت‌آمیز بود، نه کرش — خطرناک‌تر از یه خطای صریح. رفع شد به `detailPayload.data?.salon || detailPayload.salon`.
- **روش کار**: یه pass اکتشافی کامل (Explore agent) اول دقیقاً نقشه‌ی هر route + هر مصرف‌کننده‌ی فرانت‌اند رو درآورد (کدوم جا از `.data` می‌خونه و امنه، کدوم جا مستقیم از کلید legacy می‌خونه و نیاز به تغییر داره). بعد یه ایجنت پس‌زمینه (backend-dev) طبق همون نقشه‌ی دقیق، همزمان ۱۸ فایل بک‌اند + ۵ فایل فرانت‌اند رو تغییر داد. برای ۳ route (`salons`, `salon-bookings`, `salon-invites`) چون تست‌های integration موجود مستقیم روی کلید legacy می‌خوندن، اون ایجنت (طبق محدودیتی که داشت که نباید فایل تست رو دست بزنه) موقتاً کلید legacy رو نگه داشت؛ من شخصاً بعدش این ۳ مورد رو با به‌روزرسانی ۴ فایل تست (`pagination`, `authz`, `bookings`, `concurrency`) تکمیل کردم تا یکدست‌سازی واقعاً کامل بشه، نه نصفه.
- **تست واقعی و قانع‌کننده**: بعد از تکمیل، کل ۲۴ تست integration/unit pass شد؛ علاوه بر این، مسیرهایی که هیچ تست خودکاری ندارن (staff/services/hours/collabs CRUD) روی یه سرور واقعی با curl مستقیم بررسی شدن — همه دقیقاً `{data: {...}}` برمی‌گردونن، بدون هیچ کلید legacy باقی‌مونده.

- **رفع شد**: بازنویسی اتمیک با `INSERT ... ON CONFLICT (salon_user_id, artist_user_id) DO NOTHING RETURNING id` — دقیقاً همون الگوی فاز ۸. اگه ردیفی برگرده یعنی INSERT واقعی موفق بوده؛ اگه نه، یعنی تصادم رخ داده (یا دعوت قبلاً وجود داشته، یا یه درخواست هم‌زمان همین الان برنده شده) — یه SELECT روی همون ردیف (که الان قطعاً وجود داره) branch قبلی (PENDING_EXISTS / ALREADY_ACCEPTED / رفرش دوباره) رو بدون تغییر رفتار حفظ می‌کنه.

## 2026-09-30 — کد کامل Supabase Storage (dual-write؛ بدون cutover)
- **پیاده‌سازی**: `app/lib/storage.js` (جدید) — یه لایه‌ی نازک روی `@supabase/supabase-js`؛ همیشه best-effort و هیچ‌وقت throw نمی‌کنه بیرون — یعنی نبود credential یا هر خطای شبکه/آپلود فقط باعث می‌شه `null` برگرده، نه شکستن درخواست اصلی. `migrations/008_media_storage_urls.sql` سه ستون nullable جدید اضافه کرد: `users.avatar_url`, `users.poster_url`, `posts.image_url`. Dual-write مستقیم داخل تنها choke pointهای واقعی نوشتن این فیلدها قرار گرفت — `users.js`ی `createUser`/`updateUser` و `posts.js`ی `createPost`/`updatePost` (این دومی چون `salon-portfolio` هم از همین تابع رد می‌شه، خودکار پوشش داده شد). ستون‌های base64 و route های استریم `/api/media/**` دست‌نخورده و همچنان تنها منبع واقعی خواندن باقی موندن.
- **تصمیم آگاهانه**: `salon_portfolio.image`/`.tile` دست‌نخورده موند — اون جدول فقط legacy-read هست (رکوردهای نمونه‌کار جدید از طریق `posts` نوشته می‌شن)، پس اضافه‌کردن مسیر Storage براش کار اضافه روی یه مسیر نوشتن مرده بود.
- **محدودیت محیطی صریح**: این sandbox نه credential واقعی Supabase داره نه دسترسی شبکه به `supabase.com` (403 policy denial، تأیید‌شده در بخش قبلی این لاگ) — پس فراخوانی واقعی آپلود/دانلود به یه bucket واقعی **قابل تست نیست** و تست نشده. **Cutover انجام نشد** (نه route های استریم حذف شدن نه ستون‌های base64) — دقیقاً طبق احتیاط طرح اصلی فاز ۱۰.
- **چیزی که واقعاً تست و تأیید شد**: منطق خالص (`buildStorageKey`، رفتار graceful-degradation بدون credential) با ۹ تست unit جدید (`tests/unit/storage.test.js`) که هیچ‌کدوم نیاز به Supabase واقعی ندارن. مهم‌تر، کل مسیر نوشتن واقعی (ثبت‌نام → آپلود آواتار واقعی از طریق `POST /api/profile` روی یه Postgres واقعی) end-to-end تست شد: base64 درست ذخیره شد، `avatar_url` درست `NULL` موند (چون Storage تنظیم نشده) — یعنی dual-write بدون شکستن مسیر اصلی نوشتن gracefully no-op می‌کنه. کل ۱۴ تست integration موجود (که همگی توی همین محیط بدون Supabase اجرا می‌شن) هم بدون تغییر رفتار pass موندن — مدرک مستقیم که این تغییر چیزی رو نشکسته.
- **اسکریپت backfill یک‌باره** (`scripts/backfill-media-storage.mjs`) اضافه شد — ردیف‌های base64 موجود بدون `*_url` رو پیمایش و آپلود می‌کنه؛ idempotent (فقط ردیف‌های `NULL` رو دست می‌زنه)؛ حالت `--dry-run` روی یه دیتابیس واقعی seed‌شده تست و تأیید شد (شمارش درست کار می‌کنه، بدون Storage واقعی هم قابل اجراست).
- **قدم بعدی مستندشده (بعد از دیپلوی واقعی)**: تنظیم `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_STORAGE_BUCKET` (جزئیات در `.env.example`)، اجرای `node scripts/backfill-media-storage.mjs`، تأیید دستی که آپلودهای جدید واقعاً در Storage قابل‌مشاهده‌ان، و فقط بعد از اون یه migration جدا برای cutover (سوییچ خواندن‌ها + حذف ستون‌های base64) — این لاگ باید قبل از اون قدم دوباره خونده بشه.
- فایل‌های اصلی تغییر کرده: `app/lib/storage.js` (جدید)، `migrations/008_media_storage_urls.sql` (جدید)، `app/lib/db/repos/users.js`، `app/lib/db/repos/posts.js`، `scripts/backfill-media-storage.mjs` (جدید)، `tests/unit/storage.test.js` (جدید)، `.env.example`، `package.json` (`@supabase/supabase-js`).

  ```sql
      url := 'https://<your-deployed-domain>/api/cron/expire-bookings',
      headers := jsonb_build_object('Authorization', 'Bearer ' || '<CRON_SECRET واقعی>')
    );
    $$
  );
  ```
  `CRON_SECRET` باید هم در `.env`ی دیپلوی‌شده‌ی اپ و هم توی این SQL (یا بهتر، از طریق Supabase Vault) یکسان تنظیم بشه. جایگزین: هر scheduler خارجی دیگه (مثل یه GitHub Action با cron trigger) هم کار می‌کنه، چون endpoint فقط یه POST با هدر Authorization می‌خواد، وابسته به هیچ ویژگی خاص Supabase نیست.
