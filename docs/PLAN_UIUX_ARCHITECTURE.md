# پلن ارتقای زیبابان: اول UI/UX، بعد معماری

نقطهٔ شروع (ارزیابی ۴ اکتبر ۲۰۲۶): UI ≈ ۷۲، UX ≈ ۷۰، معماری فرانت ≈ ۵۲، تست ≈ ۶۰، a11y ≈ ۵۵.
هدف: UI/UX به ۸۵+ و معماری فرانت به ۷۵+ برسد، بدون اینکه رفتار فعلی بشکند.

اصل کار: هر مرحله کوچک، مستقل، با PR جدا و با اسکرین‌شات قبل/بعد. هیچ مرحله‌ای بدون تأیید شما شروع نمی‌شود.

---

## بخش اول: UI/UX

### فاز ۰ — پایه (۱ روز)
- **ممیزی بصری کامل** با Playwright: اسکرین‌شات هر صفحه و مودال در سه عرض (۳۶۰، ۳۹۰، ۴۲۸) برای هر سه نقش (مشتری، آرتیست، سالن).
- خروجی: فهرست مشکلات با شدت (بحرانی / مهم / جزئی) در `docs/UI_AUDIT.md`. از این به بعد باگ‌ها را ما پیدا می‌کنیم، نه شما با اسکرین‌شات.
- **معیار پذیرش:** هر مشکل شماره، اسکرین‌شات و بخش مربوط را دارد.

### فاز ۱ — سیستم طراحی (۲ تا ۳ روز)
مشکل ریشه‌ای که چند باگ اخیر را ساخت (برخورد specificity، ترتیب stylesheet، قواعد عمومی فرم که کنترل‌های تو در تو را خراب می‌کنند) نبودِ سیستم است.
- توکن‌های کامل در `tokens.css`: رنگ، فاصله، شعاع، سایه، z-index (فهرست لایه‌ها: dropdown، sheet، modal، toast)، تایپوگرافی.
- کامپوننت‌های پایه واحد: `Button`، `Field`، `Select`، `Sheet`/`Modal`، `Chip`، `EmptyState`، `Skeleton`، `Toast`. فعلاً هر بخش نسخهٔ خودش را دارد.
- قاعدهٔ نام‌گذاری: هر کامپوننت CSS خودش، بدون قواعد عمومی روی `input/label` داخل مودال‌ها.
- **معیار پذیرش:** مقدارهای سخت‌کد رنگ و z-index در CSS جدید صفر باشد؛ سه مودال/شیت موجود (انتخاب حوزه، کاتالوگ خدمات، فرم رزرو) روی کامپوننت پایه منتقل شوند.

### فاز ۲ — فلوهای اصلی (۱ تا ۲ هفته، به ترتیب اولویت)
1. **ورود و ثبت‌نام:** شفاف‌کردن مراحل، پیام‌های خطای فارسی و کنار فیلد، حفظ داده‌ها هنگام خطا. (آماده‌سازی برای OTP)
2. **رزرو مشتری:** از صفحهٔ سالن/آرتیست تا تأیید؛ نمایش واضح قیمت، مدت و وضعیت (در انتظار / تأیید شده)، و صفحهٔ «رزرو من».
3. **پنل آرتیست:** تب رزرو (حذف نوار روز، یک نمای برنامه)، خدمات، مرخصی.
4. **پنل سالن:** پرسنل، خدمات، ساعت کاری، برنامه روزانه.
5. **پروفایل عمومی و نمونه‌کار:** گالری، ذخیره، اشتراک.
6. **تنظیمات:** گروه‌بندی، توضیح کوتاه زیر هر گزینه، و توگل‌های «یادآوری» فقط وقتی سیستم پشتش آماده شد.
- برای هر فلو: بازبینی با چک‌لیست (حالت خالی، لودینگ، خطا، متن طولانی، اعداد فارسی، RTL، کیبورد روی موبایل).

### فاز ۳ — هویت بصری و جزئیات (۱ هفته)
- ادامهٔ بازطراحی ۱۱ دستهٔ آیکن خدمات (هر دسته با پیش‌نمایش قبل/بعد و تأیید شما، مثل ناخن).
- حرکت و بازخورد: انیمیشن باز/بسته شیت‌ها، حالت فشرده‌شدن دکمه‌ها، `prefers-reduced-motion`.
- اسکلت لودینگ به‌جای صفحهٔ خالی در همهٔ لیست‌ها.

### فاز ۴ — دسترسی‌پذیری (۳ تا ۵ روز)
- کنتراست رنگ (WCAG AA)، اندازهٔ هدف لمسی حداقل ۴۴px، ترتیب فوکوس، `aria-live` برای toastها، تله‌ی فوکوس و بستن با Esc در شیت‌ها.
- ابزار: axe روی همان اسکریپت Playwright فاز ۰.
- **معیار پذیرش:** صفر خطای بحرانی axe روی صفحات اصلی.

### فاز ۵ — تست بصری (۲ روز)
- مجموعهٔ Playwright که فلوهای ثبت‌نام، رزرو و تأیید را اجرا و اسکرین‌شات مرجع مقایسه می‌کند؛ در CI اجرا شود.
- این همان تست E2E است که در ارزیابی کم داشتیم.

## بخش دوم: معماری

شروع فقط بعد از پایان فاز ۲ بخش اول (تا دو بار روی یک کد کار نکنیم). فاز ۳ تا ۵ بخش اول می‌تواند هم‌زمان پیش برود.

### اصول
- بازسازی تدریجی (strangler)، نه بازنویسی. هر مرحله یک PR کوچک، با تست سبز قبل و بعد.
- هیچ تغییر رفتاری هم‌زمان با جابه‌جایی کد.

### فاز A — تور ایمنی (۲ تا ۳ روز)
- E2E فاز ۵ بخش اول باید آماده باشد؛ بدون آن، شکستن `HomeApp` پرخطر است.
- تست‌های رفتاری برای hookهای بزرگ (`useSalonWorkspace`، `useArtistWorkspace`) روی نقشهٔ API.

### فاز B — شکستن `HomeApp.jsx` (۱ تا ۲ هفته)
اکنون ۲٬۸۶۴ خط است و همه‌چیز از آن می‌گذرد.
- استخراج به ترتیب: (۱) پوستهٔ ناوبری و تب‌ها، (۲) مسیر هر نقش (مشتری / آرتیست / سالن) به‌صورت صفحه‌های جدا، (۳) مودال‌ها به یک مدیر مودال مرکزی.
- جایگزینی پراپ‌دریلینگ با Context محدود (session، نقش، تنظیمات) به‌جای عبور دادن ده‌ها پراپ.
- مسیریابی واقعی: هر تب یک URL (`/home/bookings` ...) تا دکمهٔ برگشت و لینک‌دهی کار کند.
- **معیار پذیرش:** `HomeApp.jsx` زیر ۴۰۰ خط؛ هیچ فایل کامپوننتی بالای ۸۰۰ خط.

### فاز C — لایهٔ داده در فرانت (۱ هفته)
- یک کلاینت API واحد (خطا، ریتری، پیام فارسی یکدست) به‌جای `fetch` پراکنده؛ همان الگوی `notifyFromResponse` ولی متمرکز.
- کش و ری‌والیدیشن ساده (SWR یا مشابه) برای لیست‌ها تا حالت «بعد از ذخیره، لیست قدیمی» پیش نیاید.
- الگوی واحد busy و optimistic (همان که برای توگل‌های تنظیمات ساختیم) به‌صورت hook مشترک.

### فاز D — سبک‌سازی CSS (۱ هفته)
- `styles.css` حدود ۲۴ هزار خط است (کل CSS حدود ۴۳ هزار خط). انتقال تدریجی به فایل کنار هر کامپوننت (CSS Modules) هم‌زمان با فازهای بالا، و حذف قواعد مرده با ابزار پوشش (coverage).
- **معیار پذیرش:** `styles.css` زیر ۵ هزار خط.

### فاز E — سرور و عملیات (موازی، ۱ هفته)
- تجمیع پیام‌های خطای API به فارسی (یک نقشهٔ مرکزی).
- مانیتورینگ خطا (Sentry یا مشابه)، لاگ ساخت‌یافته و endpoint سلامت.
- بررسی ایندکس‌ها و کوئری‌های سنگین با دادهٔ حجیم؛ بکاپ و مستندسازی بازیابی.
- (در صورت تأیید شما) OTP و سیستم یادآوری رزرو؛ این دو فیچر هستند نه معماری، ولی روی لایهٔ اعلان تأثیر می‌گذارند.

## ریسک‌ها
- شکستن `HomeApp` بدون تست E2E ریسک رگرسیون بالاست، پس فاز ۵ بخش اول پیش‌نیاز فاز B است.
- فاز ۲ با ایجاد صفحه‌های جدید ممکن است در فاز B دوباره جابه‌جا شود؛ برای همین کامپوننت‌ها را از اول مستقل از `HomeApp` می‌نویسیم.
- تخمین‌ها بدون در نظر گرفتن بازخورد شما روی هر پیش‌نمایش است.

## تصمیم‌هایی که از شما لازم است

2. آیکن‌های ۱۱ دستهٔ باقی‌مانده در فاز ۳ بیاید یا زودتر؟
3. OTP و یادآوری رزرو داخل این پلن باشد یا جدا؟
